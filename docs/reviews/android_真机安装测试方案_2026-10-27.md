- 日期：2026-10-27 ｜ 适用：`feature/android-spike` 合并后的任意含 sp-kffi 的构建
- 目的：把模拟器口径的 spike 结论（KDF 1045~1124ms / VmHWM delta≈68MiB / 8 项断言）落到真机；
  回填 SP-N-301/302（DR-009 列为 M1 前置）；为 M1b/M1c（Autofill 精度清单）准备设备侧条件

## 1. 设备与前置条件

| 项 | 要求 | 说明 |
|---|---|---|
| 设备 | Android 9.0+（minSdk 28），arm64-v8a | 建议 ≥2 台：1 台原生/Pixel 类 + 1 台厂商定制（三星/小米/OPPO 任一，R14-3 厂商差异） |
| RAM 记录 | 越低越好（对照用） | ≤4GB 设备可顺带验证 68MiB KDF 峰值是否引发卡顿/LMK |
| 开发者选项 | 设置→关于手机→连点版本号 7 次 | 厂商 ROM 可能藏在不同路径 |
| USB 调试 | 开发者选项内开启；首次连接主机弹授权 | MIUI 等需同时开"USB 安装（USB debugging install）" |
| 主机侧 | 本仓库 Android 环境已部署（adb/NDK/cargo-ndk 自检过） | `adb devices` 能看到设备 |
| 口令纪律 | **测试专用 throwaway 口令**；绝不把真实密码库装上测试设备 | 凭据只走环境变量/intent extra，不进命令行历史之外的任何持久层（SRS 红线 #5） |

## 2. 构建与安装（adb 途径，开发口径）

当前 `android/app/src/main/jniLibs/` 只有 x86_64（模拟器口径），真机需先补 arm64-v8a：

```bash
# 1. 交叉编译 arm64 .so（spike 已验证 release 1.9MB；真机测试用 debug 以便 run-as）
cargo ndk -t aarch64-linux-android --platform 28 -- build -p sp-kffi
mkdir -p android/app/src/main/jniLibs/arm64-v8a
cp target/aarch64-linux-android/debug/libsp_kffi.so \
   android/app/src/main/jniLibs/arm64-v8a/

# 2. 构建 APK（debug 构建 = debuggable，run-as 可用）
cd android && ./gradlew.bat :app:assembleDebug

# 3. 安装（USB 连接后）
adb install -r app/build/outputs/apk/debug/app-debug.apk

# 4. 生成 fixture（凭据走环境变量；真机测试建议换新口令）
mkdir -p build
SP_TEST_DB_PASSWORD=<新测试口令> SP_TEST_ENTRY_PASSWORD=<新测试条目值> \
  cargo run -q -p sp-kffi --example make_spike_vault -- build/test_vault.kdbx

# 5. 推送 fixture（/data/local/tmp → run-as 进应用私有目录）
adb push build/test_vault.kdbx /data/local/tmp/
adb shell run-as com.superpasswdkey.spike mkdir -p files
adb shell run-as com.superpasswdkey.spike cp /data/local/tmp/test_vault.kdbx files/
adb shell rm /data/local/tmp/test_vault.kdbx   # 用完即清

# 6. 启动 e2e（凭据经 intent extra；Git Bash 下必须 MSYS_NO_PATHCONV=1）
MSYS_NO_PATHCONV=1 adb shell am start -n com.superpasswdkey.spike/.MainActivity \
  --es db_password <口令> --es entry_password <条目值> --es entry_username demo-user

# 7. 采集结果（两路，互为备份）
adb logcat -d -s SPIKE
adb shell run-as com.superpasswdkey.spike cat files/result.txt
```

注：Git Bash 的 adb 路径参数需 `MSYS_NO_PATHCONV=1`（`/data/...` 会被本地路径转换）；PowerShell/cmd 无此问题。

无开发者选项的普通侧载（备用途径）：把 app-debug.apk 拷到设备点击安装（允许未知来源）——但
无法用 run-as 推 fixture，需设备有文件管理器把 kdbx 放到应用可读位置，**spike 壳不支持**，
故此途径仅 M1b 之后（应用内导入）适用，本方案不展开。

## 8. M1c 执行记录（2026-10-28 凌晨，Autofill 真机链路）

### 结果总览

| 场景 | 结果 | 证据 |
|---|---|---|
| 原生表单填充（包名匹配路径，SP-F-803） | ✅ **全通** | `fill: page=https://com.superpasswdkey.spike` → `matched [Demo Login]` → `AUTOFILLED/INPUT: username len=9 / password len=16`（值不落日志 ✓） |
| 不匹配返回空集 | ✅ | fixture 条目 url=localhost 时包名页请求返回 `no matching entries`（不猜测语义 ✓） |
| 第三方浏览器（Quark） | ⚠️ 受阻 | 服务收到 fill 请求，但 Quark 的 WebView 结构**不暴露 hints/webDomain**（Quark 自带密码管理器，禁用了系统 autofill 结构上报）→ R14-1 实锤数据 |
| 系统浏览器路径（WebView/Chrome） | ⚠️ 受阻 | MIUI 定制 AutofillManager 对 web 虚拟字段报 `view not autofillable - not passing ime action check`（配合小米安全键盘接管密码框）→ R14-3 实锤数据 |

### HyperOS 真机门禁清单（复用必读）

1. 安装：`INSTALL_FAILED_USER_RESTRICTED` → 需手机端"USB 安装"。
2. `pm clear` / `am force-stop` 被静默限制（进程仍存活）→ 用 `am start -S` 重启。
3. `pm clear`（SecurityException）、`input keyevent`（INJECT_EVENTS）、`settings put secure autofill_service`（WRITE_SECURE_SETTINGS）均被拒 → **autofill 服务只能用户手动设置**（设置→更多设置→语言与输入法→密码和账号→首选服务）。
4. MIUI 对 web 虚拟字段的 autofill 门禁（`ime action check`）+ 小米安全键盘 → 第三方服务在 web 字段填充受阻；**原生字段不受影响**。
5. `am start -S` 可绕过 force-stop 限制完成进程重建（解锁钩子依赖 onCreate）。

### KDF 夜间降频发现（SP-N-302 方法论）

同一设备（骁龙 8s Gen 3）：下午 2.2–2.5s（t=8/p=4）→ 凌晨 **8.2s → 18.3s**（同一构建）。
诊断：大核 633MHz/上限 2668MHz，电池 100%（status=5 充满）、thermal status=0（无热节流）、low_power=0
——**HyperOS 午夜睡眠模式的系统性降频**。结论：
- 真机 KDF 实测必须记录时段与电源模式，夜间数字不可作参数依据；
- DR-010（降 t + init 校准）的必要性被进一步印证：固定 t=8 在夜间降频状态下完全不可用（>18s）；
- 后续校准器（calibrate_mobile）在校准瞬间同样受降频影响 → 正式版应在解锁场景给出"当前参数预估耗时"提示或后台预派生。

### M1c 状态与后续

- 已完成：原生路径真机闭环（解锁会话 → 匹配 → 填充）；模拟器双路径（原生 + web 骨架）。

### 9. M1c 尾项：真实 Chrome 补测结论（2026-10-28 凌晨）

- 环境：Redmi Turbo 3 安装 Chrome 151.0.7922.71（arm64），autofill 首选服务=SP Spike，会话已解锁，`adb reverse` 演示页可达。
- 结果：**Chrome 内聚焦 web 字段（用户名/密码）完全不产生 onFillRequest**（服务零调用，系统 AutofillManager 无事件）。
- 证据链合并判定：MIUI/HyperOS 将 web 字段 autofill 路由至自家栈（小米密码管家 + 安全键盘），**第三方 autofill 服务在 web 字段被 ROM 策略门禁**——与 §8 中我们自身 WebView 的 `view not autofillable - not passing ime action check` 互证。
- 结论：**该数据项按"ROM 阻断"闭合**，非本项目缺陷（同设备原生字段端到端全通；模拟器无 MIUI 全通）。
- 后续：webDomain 路径的真机验证需**非 MIUI 设备**（Pixel 类原生 ROM）或 MIUI 关闭安全键盘/密码管家的替代配置（待研究）；风险条目 R14-1/R14-3 维持开放，结论已回填 design_docs/14。

### 10. 追加数据点：360极速浏览器（2026-10-28）

- 环境：360极速（com.qihoo.contents，Chromium 内核）on HyperOS，autofill 服务=SP Spike，会话已解锁，演示页经 reverse 加载成功。
- 结果：服务收到 fill 请求（两次），但结构中**无任何表单节点**（连调试 dump 均为空）——与 Quark 同款行为。
- 判定：R14-1/R14-3 的**第三个佐证数据点**。国产/第三方浏览器在 MIUI 上对 web 字段 autofill 呈现系统性不配合（浏览器侧禁用结构上报 × ROM 侧安全键盘/门禁，两层叠加）。
- 结论不变：web 路径最终验证锚点 = 非 MIUI 设备（Pixel 类原生 ROM）+ Chrome；本项目侧无缺陷可修（原生字段路径同设备全通）。

### 11. 干净 ROM 模拟器矩阵收尾（2026-10-28，x86_64 宿主机全部可行路径穷尽）

为闭合 webDomain 数据点，在干净 AOSP 模拟器上穷尽了所有可用的浏览器载体：

| 载体 | 结果 |
|---|---|
| 系统 WebView（Chromium x86_64）+ loadDataWithBaseURL | web 字段**有上报**（hints 可见）但 **webDomain=null**（data: 导航无源域） |
| 系统 WebView + 真实导航 http://localhost | 字段事件**完全不触发**（聚焦/requestAutofill/JS focus 均无 web 节点） |
| Chrome 151 arm64（手机拉取）+ Play 版镜像 ARM 翻译 | **SIGSEGV 启动崩溃**（Chrome 不兼容 ndk_translation） |
| Chromium 官方快照 | 仅 armeabi-v7a（INSTALL_FAILED_NO_MATCHING_ABIS，x86_64 镜像无 ARM 翻译） |
| Chrome x86_64 变体（apkmirror/apkpure） | 站点不可达（无代理） |
| Play 商店装 Chrome | 需 Google 登录（accounts.google.com 不可达） |
| Firefox 110 x86_64（官方 GitHub 构建） | **autofill 框架对接完整**（fill 请求+完整结构），但 webDomain=null（`page=https://`）→ 匹配无法进行 |
| ARM 版模拟器镜像 | x86_64 宿主机不支持（Google 仅发 Apple Silicon ARM 镜像） |

**结论**：
1. webDomain 数据点在本机所有可行载体上均无法产出——WebView/GeckoView 的 autofill 集成对 localhost 真实导航不上报源域；真实 Chrome 又无法在 x86_64 模拟器运行。**验证锚点维持"非 MIUI 真机 + Chrome"不变**（R14-1/R14-3 开放，证据齐备）。
2. 有价值的正向事实：**Firefox on 干净 ROM 证明平台 autofill 管线对第三方浏览器完全畅通**（MIUI 的问题确认为 ROM 层而非平台层）；服务的认证回路（锁定态 auth dataset）在 Firefox 场景被正确触发。
