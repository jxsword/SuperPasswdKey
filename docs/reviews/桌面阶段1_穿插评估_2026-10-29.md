# 桌面阶段 1 穿插评估（P2 协议加密 + 密钥复用开库；仅设计要点与工作量，不启动实现）

- 日期：2026-10-29（步骤 6 会话穿插评估，DR-009 承诺 ≤20% 预算口径内）
- 性质：评估文档——不实现、不拍板；为步骤 7（桌面阶段 1）提供排期输入

## 1. P2 协议加密（TweetNaCl box，DR-006 预留切换点）

### 现状核实
- 信封 `{v, codec, payload}` 已含 codec 字段；`decode_envelope` 对 "naclbox" 返回
  UnsupportedCodec（`crates/sp-nmhost/src/protocol.rs:67-70`）——切换点就位，业务层零感知。
- P1 明文管道的安全前提（DR-006）：native messaging 管道仅浏览器与 host 可见；对手=同用户
  内存注入者（加密层无可防增益）；allowed_origins 绑定已实现。

### 设计要点（P2 启用时）
- 照搬 KeePassXC browser-integration 握手：扩展生成密钥对 → host 持公钥注册表
  （`native-host/` 注册脚本扩展）；每次请求 = sealed box（nonce + X25519+XSalsa20-Poly1305）。
- 信封变化：payload 变 base64 密文 + `codec:"naclbox"`；握手动作 `sp.handshake`（回 host 公钥）。
- Rust 侧依赖：`crypto_box`（RustCrypto，TweetNaCl 语义等价）或引 libsodium-sys；**倾向
  crypto_box 纯 Rust**（deny 面干净、无 C 工具链负担）。
- 测试面：握手 round-trip、错公钥拒绝、重放 nonce 拒绝、大 payload 分包（native messaging
  1MB 上限与加密膨胀）。

### 工作量评估
- host 侧 codec 适配器 + 密钥管理：~1 天；extension 侧（JS）加解密：~1 天；
  握手/注册脚本/测试：~1 天。**合计 ≈3 天**（与 DR-006 当初预估一致，无下修空间）。

### 结论建议
- 维持 P2 为 backlog：当前威胁模型下无安全增益（DR-006 论证仍成立），优先级应低于
  web 路径真机验证与 Keystore DR。若启动，建议独立 feature 分支一次交付（不与其它任务混合）。

## 2. 密钥复用开库（keepass_ng 复合密钥直开可行性重估）

### 重估结果（2026-10-29 实查源码）
- 锁定版本 keepass-ng **0.11.12**（Cargo.lock），与 DR-006 当初核实版本一致。
- `Database::open(source, DatabaseKey)`（`src/db/open.rs:124`）仍要求 DatabaseKey；
  `get_key_elements()` 仍为 **pub(crate)**（`src/key/mod.rs:177`）——"以已派生密钥元素直开库"
  公开 API **仍不可用**，DR-006 方案 A（每请求重开库含 KDF，单请求 ≈KDF+<50ms）结论不变。
- 上游观察：key/mod.rs 内部已把密钥元素构造与使用分离（KeyElements 类型），公开化在 upstream
  是小改动——可关注 release notes；或 fork/patch 一行 pub（代价小但引入维护面，不推荐）。

### 替代路径（若单请求 KDF 延迟成为实测瓶颈）
- 唯一正路：给 upstream 提 PR 公开 `get_key_elements` 或提供 `DatabaseKey::from_elements`。
  预估 upstream 沟通+合并周期 1–4 周，host 侧改造 <0.5 天（构建 DatabaseKey 等价物）。
- 在此之前无需任何代码动作。
